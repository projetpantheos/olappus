# 10 — Muses / Knowledge Governance

## Principe

Muses apprend des faits, pas des personnes.

Séparation :
USER STATE ≠ PRODUCT LEARNING ≠ COLLECTIVE KNOWLEDGE

## Pipeline

SOURCE → OBSERVATION/FACT → PROPOSAL → INDEPENDENT REVIEW → CERTIFICATION → PUBLICATION

## États

UNVERIFIED
PROPOSED
UNDER_REVIEW
VALIDATED
CERTIFIED
PUBLISHED
SUSPENDED
RETIRED

## Sources

Hiérarchie :
OFFICIAL > CERTIFIED > VALIDATED > COMMUNITY > AI

Mais la résolution tient aussi compte de :

- juridiction ;
- date/effective date ;
- spécificité ;
- contexte ;
- certification ;
- contradictions.

La source « perdante » est conservée avec la résolution.

## Validation critique

2 validations humaines indépendantes + 1 validation certifiée pour les règles critiques.
Des comptes liés ne constituent pas artificiellement un quorum.

## AI

L'IA peut proposer.
Elle ne peut jamais créer directement une connaissance validée/certifiée.

## Provenance

Chaque connaissance/règle importante conserve :

- source ;
- version ;
- dates de validité ;
- reviewers ;
- confidence ;
- evidence ;
- historique de décision.

L'identité des contributeurs n'est pas exposée dans la connaissance publique.

## Contradictions

Créer KNOWLEDGE_CONFLICT.
Une règle publiée peut être SUSPENDED, puis REVIEW → REPUBLISHED ou RETIRED.
Pas de modification silencieuse.

## Temporalité

valid_from / valid_until obligatoires pour les connaissances/règles temporelles.

## Public

Muses public n'est pas requis au lancement.
Phase 1 : équipe Olappus + sources officielles + IA assistée.
Phase 2 : contributeurs sélectionnés.
Phase 3 : communauté.
